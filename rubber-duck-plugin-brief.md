# Бриф: плагин Rubber Duck для JetBrains IDE

> Бриф самодостаточный: писан для агента, который читает его без контекста переписки.
> Если по ходу всплывёт API, в котором не уверен, — сверяйся с исходниками целевой
> версии IntelliJ (github.com/JetBrains/intellij-community), а не угадывай.

## Что строим

Плагин для IntelliJ-based IDE: резиновая уточка живёт **оверлеем в пустом месте
редактора** и реагирует "лицом" на состояние проекта. Это буквализация ритуала
rubber-duck debugging — утка молчит, кивает, иногда крякает, паникует на красной
сборке. Пользы ноль, удовольствие максимальное. Это и есть цель.

Ключевой UX-принцип, который нельзя терять: на "расскажи утке" утка **не отвечает
по смыслу и ничего не анализирует** — просто молча кивает. Вся соль ритуала в том,
что объяснение проблемы вслух/текстом помогает само по себе. Не превращать в чат-бота.

## Стек (не отклоняться без явной причины)

- Kotlin
- **IntelliJ Platform Gradle Plugin 2.x** (org.jetbrains.intellij.platform) — НЕ старый
  gradle-intellij-plugin 1.x
- JDK 21
- Целевая платформа: IntelliJ IDEA Community, последняя стабильная — версию вынести
  в `gradle.properties` (platformVersion), чтобы легко двигать
- UI на Swing (как весь Platform UI)
- Поддержка нового UI обязательна (старый можно игнорировать)

## Архитектура — три независимых модуля

1. **Где живёт** — оверлей в пустом месте редактора (Модуль 1)
2. **Что триггерит настроение** — два источника событий пишут в DuckMoodService (Модуль 2)
3. **Реакция** — рендер/анимация кадров по текущему mood + попап-ритуал (Модуль 3)

Связующее звено — `DuckMoodService` (project-level light service), хранит текущий
`Mood`. Модуль 2 в него пишет, Модуль 1/3 из него читают и перерисовываются.

```kotlin
enum class Mood { IDLE, HAPPY, PANIC, NOD }

@Service(Service.Level.PROJECT)
class DuckMoodService {
    @Volatile var mood: Mood = Mood.IDLE
        private set
    fun setMood(m: Mood) { mood = m /* + уведомить слушателей оверлея, см. ниже */ }
}
```

## Модуль 1: Где живёт утка — оверлей в ПУСТОМ месте редактора

### Принципиальное ограничение (заложено в дизайн)
"Пустоту" можно надёжно определить **только внутри редактора** — это текстовая
сетка с известной геометрией. Тулбары, кнопки, панели tool window — непрозрачные
Swing-компоненты, их "пустоту" не спросить, а гадать по пикселям дорого и хрупко.
**Поэтому утка живёт исключительно в whitespace редактора и НЕ лезет на код, каретку,
тулбары и панели.** Это не компромисс, это скоуп.

### Куда вешать
Вешать на **`editor.contentComponent`**, а не на фрейм — тогда координаты сразу в
системе редактора и клиппинг по его границам бесплатный.
- Рисование (без клика): `IdeGlassPaneUtil.installPainter(editor.contentComponent, painter, disposable)`,
  где `painter : com.intellij.openapi.ui.Painter` (методы `paint(Component, Graphics2D)` и `needsRepaint()`).
  Painter НИКОГДА не перехватывает мышь — окно остаётся рабочим.
- Если нужен клик по утке (открыть попап) — вместо/в дополнение к Painter повесить
  **bounded `JComponent`** на `contentComponent` с габаритами СТРОГО по спрайту утки
  (`isOpaque = false`), чтобы кликабельной была только утка, а не весь редактор.
  Главный антипаттерн жанра: повесить на glass pane что-то, что съедает все клики по IDE. Не делать так.

### v1 — якорь в пустой полосе под последней строкой (делать первым)
```
editor    = FileEditorManager.getInstance(project).selectedTextEditor ?: return
document  = editor.document
lastY     = editor.offsetToXY(document.textLength).y + editor.lineHeight
visible   = editor.scrollingModel.visibleArea            // Rectangle
emptyTop  = max(lastY, visible.y)
emptyRect = Rectangle(visible.x, emptyTop, visible.width, visible.maxY - emptyTop)
```
- Если `emptyRect` по высоте вмещает спрайт → поставить утку в его правый-нижний угол (с отступом).
- Если не вмещает → утка прячется или уменьшается (нет места — не лезем на код).

### v2 — выбор наибольшего пустого прямоугольника (включать, только если зайдёт)
- Кандидат A: пустая полоса снизу (как в v1).
- Кандидат B: поле справа от кода — пробежать видимые строки, для каждой взять
  X конца строки `editor.offsetToXY(lineEndOffset).x`, найти максимум; всё правее свободно.
- Выбрать прямоугольник, который больше / куда влезает спрайт.

### Динамика (ОБЯЗАТЕЛЬНА для обеих версий)
Пустое место постоянно ездит при скролле/печати/ресайзе, поэтому цель пересчитывается:
- `VisibleAreaListener` (скролл/ресайз) + `DocumentListener` (печать), оба с дебаунсом
  через `Alarm` (~150–250 мс).
- Утка НЕ телепортируется: плавный подъезд к новой цели (`javax.swing.Timer`, easing).
  Это движение само по себе и создаёт "живость".
- Если цель пересекает caret / текущую строку — сместить утку в сторону.

## Модуль 2: Источники настроения (нужны ОБА)

Оба пишут в `DuckMoodService.setMood(...)`. Подписки вешать на
`project.messageBus.connect(disposable)`, где disposable привязан к проекту.

### a) Момент истины — компиляция
- Топик `CompilerTopics.COMPILATION_STATUS`, слушатель `CompilationStatusListener`.
- `compilationFinished(aborted, errors, warnings, context)`:
  `errors > 0 → Mood.PANIC`, иначе → `Mood.HAPPY` (через пару секунд вернуть в IDLE через Alarm).

```kotlin
project.messageBus.connect(disposable).subscribe(
    CompilerTopics.COMPILATION_STATUS,
    object : CompilationStatusListener {
        override fun compilationFinished(aborted: Boolean, errors: Int, warnings: Int, context: CompileContext) {
            service.setMood(if (errors > 0) Mood.PANIC else Mood.HAPPY)
        }
    }
)
```

### b) Живое настроение — пока печатаешь
- `WolfTheProblemSolver.getInstance(project)` — есть ли сейчас ошибки в проекте без
  полной сборки (искать актуальный метод вида `hasProblemFilesBeneath(...)` /
  `hasProblemFiles()` в целевом SDK — **сверить сигнатуру**, она менялась).
- Опрашивать с дебаунсом (`Alarm`), не на каждый keystroke. Есть ошибки → лёгкий PANIC/обеспокоенность, нет → IDLE.

## Модуль 3: Реакция и ритуал

### Кадры по настроению
- Набор статичных кадров на каждый mood: IDLE (можно 2–3 кадра дыхания), HAPPY, PANIC, NOD.
- Переключать по `Mood`; НЕ тащить видео/gif-движок — обычные изображения + смена кадра.
- Анимация (циклы дыхания, кивок) — `javax.swing.Timer` или `Alarm`, перерисовывать
  ТОЛЬКО bounds утки, не весь pane (перф).

### Ритуал "Tell the duck"
- Клик по утке (bounded-компонент) ИЛИ `AnAction` с хоткеем → лёгкий попап (`JBPopup`):
  большая утка + поле ввода "расскажи, что не так".
- На ввод/отправку: утка проигрывает NOD (кивок), опционально через ~1–2 c "кряк"
  (звук или визуальный пузырь) через `Alarm`. Текст НИКУДА не уходит и не анализируется.

## Сквозные правила (gotchas)

- **EDT**: весь UI, смена mood, позиционирование, перерисовка — строго на EDT
  (`ApplicationManager.getApplication().invokeLater {}`). Слушатели компилятора прилетают не с EDT.
- **Анимация**: только `Timer`/`Alarm`, НИКОГДА не `Thread.sleep` в своём треде — повесишь EDT.
- **Dumb mode**: при индексации часть API недоступна. Сервис/оверлей сделать `DumbAware`
  или оборачивать в `DumbService`; на время индексации утка может показывать "думаю".
- **Disposable**: каждую подписку/painter/слушатель привязывать к project-level disposable,
  иначе утечка при закрытии проекта.
- **Несколько проектов/окон**: оверлей per-project. Регистрировать на каждый открытый
  редактор/проект, корректно снимать при закрытии. Переключение selected editor —
  переносить утку на активный редактор.
- **HiDPI**: все размеры/отступы через `JBUIScale.scale(...)`. Спрайты — с учётом ретины (@2x или SVG).
- **Прозрачность**: PNG с alpha (или SVG); компонент `isOpaque = false`; для bounded-компонента
  переопределить `contains()`, чтобы клики проходили мимо прозрачных пикселей.
- **Z-order**: модальные диалоги/попапы должны быть ВЫШЕ утки — это нормально, не чинить.

## Чего НЕ делать

- НЕ рисовать вне редактора (тулбары/панели/кнопки) — там whitespace не детектится.
- НЕ перекрывать код, caret и текущую строку.
- НЕ перехватывать глобально мышь/клавиатуру — кликабельна только сама утка.
- НЕ использовать gradle-intellij-plugin 1.x.
- НЕ превращать "tell the duck" в LLM-чат. Утка молчит.

## Ассеты, которые нужны (заглушки на старте — ок)

- Спрайты утки на каждый mood: `idle` (2–3 кадра), `happy`, `panic`, `nod`. PNG @2x или SVG.
- Иконка плагина (`pluginIcon.svg`).
- (Опц.) звук "кряк" для ритуала.
На старте — простые плейсхолдеры; финальные кадры подсунет человек.

## Порядок сборки (milestones)

1. Скелет: build.gradle.kts (Platform Gradle Plugin 2.x), plugin.xml, `runIde` запускается.
2. `DuckMoodService` + ручной переключатель mood (временный AnAction) для проверки рендера.
3. Модуль 1 v1: статичная утка в пустой полосе под последней строкой, реагирует на mood.
4. Модуль 1 динамика: пересчёт по скроллу/печати + плавный подъезд.
5. Модуль 2a: компиляция → PANIC/HAPPY. Затем 2b: Wolf → живое настроение.
6. Модуль 3: попап "tell the duck" + кивок/кряк.
7. (Опц.) Модуль 1 v2: поле справа + выбор большего пустого прямоугольника.

## Definition of done для v1

Открываешь короткий .kt файл → утка сидит в пустоте под кодом, дышит. Ломаешь
синтаксис → пакетная сборка с ошибкой → утка паникует. Кликаешь → попап, печатаешь
"почему это не работает" → утка кивает. На код/каретку/тулбары не наезжает,
окно полностью рабочее.
